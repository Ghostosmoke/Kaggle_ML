В ваших 5 ноутбуках балансировка реализована на **трёх разных уровнях**: при разбиении данных, внутри функции потерь моделей и на этапе принятия финальных решений. Ни в одном из случаев данные физически не копируются и не удаляются (нет oversampling/undersampling) — вместо этого алгоритмы **математически меняют цену ошибки** или **смещают границу решения**.

Ниже подробный, пошаговый разбор того, как именно это работает в каждом проекте, с объяснением механизмов «под капотом».

---

### 🔹 УРОВЕНЬ 1: Балансировка на этапе разбиения данных (`StratifiedKFold`)
**Где:** `bind-reverse`, `http-malware`, `dga-v2`, `wtf-whos-talking`, `titanic`  
**Код:** `StratifiedKFold(...)`, `train_test_split(..., stratify=y)`  
**Как работает:**  
Алгоритм не просто перемешивает строки, а **сохраняет исходную долю классов** в каждом фолде.  
*Пример:* При дисбалансе 46:1 (202 malware / 9320 clean) каждый из 5 фолдов получит ровно ~20% всех `1` и ~20% всех `0`.  
**Зачем:** Если этого не сделать, в некоторых фолдах может оказаться 0 вредоносных команд → метрики станут бессмысленными, модель не научится их распознавать.

### 🔹 УРОВЕНЬ 2: Балансировка внутри моделей (изменение функции потерь)

Здесь данные остаются как есть, но **ошибка на редком классе штрафуется сильнее**. Это меняет градиенты при обучении.

#### 📘 1. `bind-reverse (1).ipynb` — `class_weight='balanced'`
**Код:** 
```python
LogisticRegression(class_weight='balanced')
RandomForestClassifier(class_weight='balanced')
LinearSVC(class_weight='balanced')
```
**Механика:**  
sklearn автоматически вычисляет вес каждого класса по формуле:
```
w_class = n_samples / (n_classes × n_samples_in_class)
```
Для дисбаланса 9320:202:
- `w_clean ≈ 9522 / (2 × 9320) ≈ 0.51`
- `w_malware ≈ 9522 / (2 × 202) ≈ 23.57`

**Что происходит при обучении:**  
Функция потерь умножается на эти веса. Ошибка на одном `malware`-примере стоит в **46 раз дороже**, чем ошибка на `clean`. Градиенты миноритарного класса увеличиваются, гиперплоскость/дерево смещаются в его сторону.  
**NB исключение:** `MultinomialNB` не поддерживает `class_weight`. Вместо этого используется `alpha=0.1` (сглаживание Лидстона), которое предотвращает обнуление вероятностей при встрече редких токенов, косвенно помогая не игнорировать миноритарный класс.

#### 📘 2. `http-malware (4).ipynb` — `class_weight='balanced'` + LightGBM
**Код:** 
```python
LogisticRegression(class_weight='balanced')
lgb.LGBMClassifier(class_weight='balanced')
```
**Механика для LR:** Аналогично выше.  
**Механика для LightGBM:**  
Параметр `class_weight='balanced'` в sklearn-обёртке транслируется во внутренний механизм C++ как автоматический расчёт весов для каждого примера. При построении каждого дерева LightGBM вычисляет **gain** (выигрыш от разбиения). Веса классов меняют формулу gain:
```
gain = (sum_grad_left² / sum_hess_left) + (sum_grad_right² / sum_hess_right)
```
`grad` и `hess` для malware-примеров умножаются на `~1.7`. Деревья чаще выбирают признаки, которые разделяют malware, даже если таких примеров меньше.

#### 📘 3. `dga-v2 (1).ipynb` — `scale_pos_weight`
**Код:** 
```python
scale_pos_weight = n_neg / n_pos ≈ 1.248
CatBoostClassifier(scale_pos_weight=1.248)
```
**Механика:**  
CatBoost работает с логарифмической функцией потерь (`Logloss`). Параметр `scale_pos_weight` **умножает градиенты и гессианы только для класса `1`**:
```
L = - [ log(p) + scale_pos_weight × (1-y) × log(1-p) ]
```
На практике это значит: при ошибке на DGA-домене модель получает в 1.25× более сильный "пинок" для обновления весов, чем при ошибке на легитимном домене. Это компенсирует перекос без изменения датасета.

#### 📘 4. `wtf-whos-talking-first.ipynb` — Явной балансировки нет
**Почему:** Задача многоклассовая (`app_service`), распределение относительно равномерное.  
**Как компенсируется:**  
- `StratifiedKFold` сохраняет пропорции.
- `BatchNormalization` стабилизирует градиенты, не давая доминирующим классам "задавить" остальные.
- `Dropout(0.4/0.3)` предотвращает ко-адаптацию нейронов на частых паттернах.
- Метрика `macro F1` принудительно усредняет F1 по всем классам, штрафуя модель за пропуск редких приложений.

#### 📘 5. `titanic-08.ipynb` — KNN не использует функцию потерь
**Почему:** KNN — instance-based алгоритм. Он не обучает веса, а запоминает данные и считает расстояния. `class_weight` к нему не применим.  
**Как балансируется:**  
- `StandardScaler` приводит признаки к одному масштабу, чтобы евклидово расстояние не перекашивалось в сторону числовых признаков с большим диапазоном (`Fare`).
- `StratifiedKFold` внутри `RandomizedSearchCV` гарантирует, что валидационные фолды отражают реальное распределение.
- Найденный параметр `weights='uniform'` означает, что все 18 соседей учитываются поровну, без приоритета по классам.

### 🔹 УРОВЕНЬ 3: Балансировка на этапе принятия решений (Threshold Tuning)
**Где:** `bind-reverse`, `http-malware`  
**Код:** 
```python
for thresh in np.arange(0.1, 0.9, 0.01):
    preds = (proba >= thresh).astype(int)
    f1 = f1_score(y_true, preds)
```
**Механика:**  
Стандартный порог `0.5` оптимален только при сбалансированных данных и одинаковой цене ошибок. При дисбалансе модель часто выдаёт вероятности в диапазоне `0.3–0.7`.  
- Сдвиг порога **вверх** (напр., `0.62`) → повышает Precision, снижает Recall (меньше ложных срабатываний).  
- Сдвиг порога **вниз** (напр., `0.49`) → повышает Recall, снижает Precision (ловим больше malware, но больше шума).  

В `bind-reverse` оптимум `0.62` отсекает "шумные" чистые команды, которые случайно набрали высокую вероятность, максимизируя `F1`. Это **инференс-балансировка**: данные не меняются, меняется лишь линейка, по которой мы отрезаем `0` от `1`.

### 🔍 ЧТО БУДЕТ, ЕСЛИ УБРАТЬ БАЛАНСИРОВКУ? (На примере `bind-reverse`)
1. Убираем `class_weight='balanced'` → LR/SVC начинают предсказывать `0` в 95% случаев.
2. `F1` для класса `1` падает с `~0.98` до `~0.15`.
3. `Accuracy` остаётся `~98%` (иллюзия качества).
4. Оптимизация порога не спасает: вероятности сжимаются к `0.0–0.1`, модель "не верит" в наличие malware.
5. В продакшене SOC-аналитик не увидит ни одной атаки.
